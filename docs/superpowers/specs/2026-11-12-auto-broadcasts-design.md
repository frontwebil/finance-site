# Щоденні авторозсилки в Telegram через cron-job.org

Дата: 2026-11-12

## Навіщо

Замовник хоче, щоб бот сам щодня розсилав повідомлення користувачам у вказаний час, без того щоб адмін вручну натискав «Запустити розсилку» і тримав вкладку відкритою. Налаштування розсилки — ті самі, що в ручній: текст, тип кнопки (Mini app / посилання / без кнопки), текст кнопки, посилання. Таких розсилок може бути кілька; їх можна додавати, редагувати, вимикати й видаляти. Замовник має бачити, що розсилка пройшла, і що пішло не так, якщо не пройшла.

## Цілі

- Нова вкладка адмінки **«Розсилки»** (`/admin/broadcasts`) у бічному меню поряд із «Головна / Користувачі / Офери».
- Список щоденних розсилок: створити, редагувати, увімкнути/вимкнути, видалити.
- Кожна розсилка відправляється **щодня у свій час за Києвом** усім користувачам з таблиці `User`.
- Відправку запускає **cron-job.org**, який щохвилини викликає захищений ендпоінт сайту.
- Розсилка доходить до кінця навіть при великій базі, падіннях і перезапусках, і **нікому не приходить двічі за день** (окрім обмеженого випадку, описаного нижче).
- **Логи**: журнал подій (запуск, завершення, помилки, пропуски) і зведення помилок Telegram по кожному запуску, видимі в адмінці.
- Індикатор «cron живий / cron мовчить», щоб замовник одразу бачив, що cron-job.org перестав викликати сайт.

## Не цілі

- Не змінюємо ручну розсилку на сторінці «Користувачі» — вона лишається як є (тільки спільний код відправки виноситься в `lib/`).
- Розклад «по днях тижня», разові розсилки на дату, сегментація користувачів, медіа (фото/відео), тестова відправка собі — не зараз. Модель даних не повинна цьому заважати (поле `nextRunAt` дозволяє додати інші розклади пізніше).
- Не інтегруємось з API cron-job.org (не створюємо там завдання програмно) — одне завдання налаштовується вручну один раз.

## Анти-цілі (провал, навіть якщо «працює»)

- Користувач отримує ту саму щоденну розсилку двічі за день.
- Після кількагодинного простою сайту/cron бот вивалює «вчорашні» розсилки пачкою.
- Будь-хто, хто знає URL ендпоінту, може запустити розсилку.
- Розсилка мовчки не відбулась, і в адмінці цього не видно.

## Обмеження

- Next.js 16.4 з `cacheComponents: true`, App Router, Route Handlers. Перед кодом читати `node_modules/next/dist/docs/` (див. `AGENTS.md`). `maxDuration` і `after()` з `next/server` доступні для Route Handlers.
- Prisma 7 + PostgreSQL (`prisma7.config.ts`, міграції в `prisma/migrations`, якої поки нема — у репо лише `schema.prisma`).
- Хостинг, імовірно, Vercel (у `.gitignore` є `.vercel`) — тобто функції з обмеженим часом виконання. Закладаємось на `maxDuration = 60`.
- cron-job.org має таймаут відповіді (~30 с на безкоштовному плані — **перевірити**). Тому ендпоінт відповідає одразу, а роботу робить в `after()`.
- Ліміт Telegram — близько 30 повідомлень/с на бота. Тримаємо ≤ 25/с. На `429` поважаємо `retry_after`.
- Авторизація адмінки — cookie `admin_session` (`lib/auth.ts`, `verifySession`). Cron-ендпоінт cookie не має — окремий секрет `CRON_SECRET`. `proxy.ts` матчить лише `/admin/:path*`, тож `/api/cron/*` він не чіпає.

## Підходи

| | Підхід | Плюси | Мінуси |
|---|---|---|---|
| **A (обрано)** | Одне завдання на cron-job.org щохвилини викликає `/api/cron/broadcasts`; розклад і прогрес — у нашій БД | Налаштовується один раз; уся логіка й стан в одному місці; стійко до падінь | Сайт «прокидається» щохвилини навіть коли нема роботи (дешевий запит) |
| B | Окреме завдання на cron-job.org на кожну розсилку через їхній REST API | Виклик точно у потрібний час | Два джерела правди, які треба синхронізувати; ліміти їхнього API; відправку пачками все одно робити в нас |
| C | Vercel Cron | Без зовнішнього сервісу | На безкоштовному плані — раз на добу й неточно; замовник просив cron-job.org |

Замовник обрав **A**.

## Дизайн

### Дані (Prisma)

**`BroadcastSchedule`** — щоденна розсилка:
- `id` (uuid), `title` (внутрішня назва для списку, обов'язкова)
- `message` (HTML, як у ручній), `buttonType` (`miniapp` | `link` | `none`), `buttonText?`, `buttonUrl?`
- `sendTime` — рядок `"HH:MM"` за Києвом
- `isActive` (bool, default true)
- `nextRunAt` (DateTime UTC, nullable коли вимкнено) — наступний момент запуску
- `createdAt`, `updatedAt`

**`BroadcastRun`** — один запуск розсилки:
- `id`, `scheduleId` (FK, `onDelete: Cascade`), `scheduledFor` (DateTime UTC — той `nextRunAt`, з якого створено запуск)
- **знімок** контенту: `message`, `buttonType`, `buttonText?`, `buttonUrl?` — редагування розсилки не змінює вже запущену відправку
- `status`: `running` | `done` | `failed` | `skipped`
- `maxUserId` (знімок аудиторії на момент старту), `cursor` (останній оброблений `User.id`)
- `sent`, `failed` (лічильники)
- `errorSummary` (Json: `{ "<опис помилки Telegram>": кількість }`)
- `lockedUntil` (DateTime, nullable) — оренда, щоб два паралельні виклики cron не відправляли один запуск
- `startedAt`, `finishedAt?`
- `@@unique([scheduleId, scheduledFor])` — гарантія «один запуск на один слот»

**`BroadcastLog`** — журнал подій:
- `id`, `createdAt`, `level` (`info` | `warn` | `error`), `message` (людський текст українською), `scheduleId?`, `runId?` (без жорсткого FK або `SetNull`, щоб логи переживали видалення розсилки), `details?` (Json)

**`CronHeartbeat`** — один рядок (`id = 1`), `lastCalledAt` — коли cron востаннє успішно викликав ендпоінт.

### Розрахунок `nextRunAt`

- При створенні, зміні `sendTime` або вмиканні: `nextRunAt` = найближчий момент `sendTime` за `Europe/Kyiv` **строго після зараз**. Тобто розсилка, створена о 15:00 з часом 10:00, вперше піде завтра о 10:00; створена о 09:00 — сьогодні о 10:00.
- Після створення запуску: `nextRunAt` = той самий час наступного дня за Києвом (з урахуванням переходу на літній/зимовий час — рахувати через `Intl.DateTimeFormat` з `timeZone: "Europe/Kyiv"`, без нових залежностей, або через невелику утиліту в `lib/`).
- Вимкнення: `nextRunAt = null`. Незавершений запуск при вимкненні **продовжується** (це вже почата відправка); видалення розсилки — зупиняє її (каскад).

### Ендпоінт `GET|POST /api/cron/broadcasts`

1. Перевірка `Authorization: Bearer <CRON_SECRET>` через `timingSafeEqual`. Інакше `401` + `console.warn` (у `BroadcastLog` не пишемо, щоб сміттєві запити не засмічували журнал). Якщо `CRON_SECRET` не задано — `500`.
2. Оновити `CronHeartbeat.lastCalledAt`, одразу відповісти `200 { ok: true }`, решту роботи — в `after()`. `export const maxDuration = 60`.
3. У `after()`:
   - **Планування.** Для кожної `BroadcastSchedule` з `isActive` і `nextRunAt <= now`:
     - якщо `now - nextRunAt > 3 год` — створити запуск зі статусом `skipped`, лог `warn` «Пропущено: cron не викликався вчасно», зсунути `nextRunAt` на наступний день;
     - інакше створити `BroadcastRun` (`running`, знімок контенту, `maxUserId` = поточний максимальний `User.id`, `cursor = 0`), лог `info` «Розсилку розпочато», зсунути `nextRunAt`. Створення запуску і зсув `nextRunAt` — в одній транзакції; конфлікт `@@unique` = інший виклик уже створив, тихо пропускаємо.
   - **Відправка.** Брати запуски `running`, атомарно «захоплюючи» кожен через `updateMany where lockedUntil is null or < now` → `lockedUntil = now + 70 с`. Відправляти користувачам `id > cursor AND id <= maxUserId` по зростанню, з темпом ≤ 25 повідомлень/с, доки не вичерпано бюджет **~45 с** на весь виклик. Після кожних ~25 повідомлень записувати `cursor`, `sent`, `failed`, `errorSummary`.
   - Коли користувачі закінчились — `status = done`, `finishedAt`, зняти `lockedUntil`, лог `info` «Завершено: успішно N, помилок M» (якщо M > 0 — рівень `warn` і топ помилок у `details`).
   - Бюджет вичерпано — записати прогрес, зняти `lockedUntil`; наступна хвилина продовжить.
4. **Помилки Telegram:**
   - `429` → зупинити цей запуск у поточному виклику, лог `warn` з `retry_after`, продовжити наступного разу (цей користувач не вважається обробленим).
   - `400/403` по конкретному користувачу (заблокував бота, чат не знайдено тощо) → `failed += 1`, `errorSummary[description] += 1`, рухаємось далі. Окремих логів на кожного користувача не пишемо.
   - Невалідний токен / відсутній `BOT_TELEGRAM_TOKEN` / `401` від Telegram → `status = failed`, лог `error`, запуск зупинено.
   - Помилка контенту, яка вбиває кожне повідомлення (напр. `can't parse entities` — битий HTML): якщо перші 25 спроб запуску всі впали з тим самим `400` — `status = failed`, лог `error` з описом. Щоб не «спалити» всю базу битою розсилкою.
   - Будь-який неочікуваний виняток — лог `error`, `console.error`, оренда спадає сама через `lockedUntil`.
5. **Прибирання:** раз на виклик видаляти `BroadcastLog` старші 30 днів (дешевий `deleteMany`).

**Повторні повідомлення:** якщо процес впаде між відправкою і записом `cursor`, до ~25 користувачів можуть отримати повідомлення двічі. Прийнятно; зменшується частішим записом прогресу.

### Спільний код

- `lib/telegram.ts` — `sendTelegramMessage({ chatId, text, button })`, що повертає `{ ok, status, description, retryAfter }`; побудова `reply_markup` з `buttonType/buttonText/buttonUrl`. Ручна розсилка (`app/api/admin/send-broadcast/route.ts`) і cron використовують його.
- `lib/broadcast-validation.ts` — та сама валідація, що зараз у ручній розсилці (текст обов'язковий; текст кнопки обов'язковий, якщо кнопка є; `http/https` для посилання) + `sendTime` формату `HH:MM`.

### Адмін-API (усі з `verifySession()`)

- `GET /api/admin/broadcasts` — список розсилок з останнім запуском кожної + `lastCalledAt` cron.
- `POST /api/admin/broadcasts` — створити.
- `PATCH /api/admin/broadcasts/[id]` — редагувати / увімкнути / вимкнути (перераховує `nextRunAt`).
- `DELETE /api/admin/broadcasts/[id]`.
- `GET /api/admin/broadcasts/logs?scheduleId=&level=&cursor=` — журнал, найновіші зверху, пагінація по 50.

- Форма створення/редагування — модалка з тими самими полями, що в `SendBroadcast.tsx`, + «Назва» і «Час (Київ)» (`<input type="time">`). Підказка, що HTML форматування підтримується.
- Видалення — `window.confirm`; якщо запуск зараз іде — попередити, що відправку буде зупинено.
- Статус cron: «активний», якщо `lastCalledAt` < 3 хв тому, інакше попередження.

### Налаштування cron-job.org (у README)

1. Додати в `.env` (і на хостингу) `CRON_SECRET=<довгий випадковий рядок>`.
2. cron-job.org → **Create cronjob** → URL `https://<домен>/api/cron/broadcasts`, розклад **Every minute**.
3. **Advanced → Headers**: `Authorization: Bearer <CRON_SECRET>`.
4. Увімкнути сповіщення cron-job.org про невдалі виклики (опційно).
